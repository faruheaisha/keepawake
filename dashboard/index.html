      02

      保护是否真的有效

      数据来自内核电源日志（Kernel-Power 506/507、Power-Troubleshooter），普通用户权限即可读。软件说自己没睡不算证据 —— 睡过就是睡过。

      —
      这些结论是什么意思？

      结论按内核电源日志逐条归因：「被绕过」= 电源请求还在被持有，机器却睡了，这是平台无视请求的唯一实锤；「睡眠时无请求持有」= 睡过，但那一刻没人要求保持清醒，责任不在保护；「无从判断」= 时间早于保留日志的覆盖范围，既不自证清白也不归罪；「仅熄屏」= 屏幕黑了但系统没有离场，506 事件也会计入它，所以不能只看 506 的数字。下方的筛选只是观察视角，不改变上面任何一个数字。

      筛选只是查看视角，上方结论与统计仍按整个时间窗计算

      真睡眠（请求正被持有 → 被绕过） 真睡眠（当时没有任何请求） 真睡眠（ka.log 够不到，无法判定） 菱形 = Kernel-Power 42 的入睡转换（经典 S3 / 休眠）：填充、空心、虚线的含义与上面三个圆点相同 仅熄屏，未睡 唤醒 / 恢复 保护区间 —

      03

      本机环境适配

      逐条从 powercfg / 注册表实读，交流电与电池分开。心跳建议值由本机最短锁屏计时推导，不是抄来的通用数字。

      这些风险从哪来？

      每一条都从 powercfg / 注册表 / 系统能力实时读取，不是缓存。标红的项会真实打断无人值守（比如合盖睡眠，任何软件都拦不住）；标黄的项需要注意但不必然出问题。心跳建议值由本机最短锁屏计时推导，不是通用数字。

      04

      远程无人值守

      看门狗是计划任务，不靠面板窗口活着：登录自动启动、每 10 分钟按 intent.json 对账。人对不上机器的时候，自愈就是主功能而不是附加项。

      —
      对账规则
      • intent=awake 且未到期 且没有 worker → 拉起，并恢复剩余时长。
      • intent=off → 看门狗什么都不做。你手动停止后它不会把你停的东西又开起来。
      • 定时保护到期 → 视为已了结，不会再被复活（到期不是故障）。
      • 参数不写 intent → 重启后按 config.json 起。要让某组参数长期生效，点「存为默认」。

      06

      能力边界

      这一栏写的是「做不到什么」。防休眠软件最常见的失败是让人以为它无所不能。

      对照 PowerToys Awake / Caffeine / mouse jiggler 的公开行为整理
      能压住
      • 空闲时自动进入的系统休眠 / 现代待机（ES_SYSTEM_REQUIRED）
      • 空闲时显示器熄灭（ES_DISPLAY_REQUIRED）
      • 空闲锁屏计时与需密码的屏保（心跳重置空闲计时）
      • OEM 电源管理中途抢占请求（按「重新声明」周期再申请）
      • 重启、崩溃、被强杀后的自动恢复（计划任务看门狗）
      压不住
      • Win+L、开始菜单→电源→锁屏：显式操作，任何软件都不该去拦
      • 合上屏幕盖：传感器触发，除非改掉合盖动作本身
      • 心跳穿透不了锁屏：已锁屏时输入不会送到会话里，只会显示在锁屏界面上
      • 组策略强制维护窗口、电池耗尽保护、平台强制待机
      • 动态锁（手机蓝牙）、第三方安全软件的自行锁定 —— 本机读不到
      怎么验证
      • 启动保护 → 让机器空闲 10 分钟 → 看 02 的「进入待机」次数
      • 合盖实测：ka.bat lid -LidAction apply（自带备份，restore 可还原）
      • 到底是谁在起作用：ka.bat status 的「同类软件」一行
      • 是待机还是只是熄屏：ka.bat evidence 两者成因不同
      — 所有请求只走向 127.0.0.1 · 面板不带跨域许可，外部页面无法驱动它
