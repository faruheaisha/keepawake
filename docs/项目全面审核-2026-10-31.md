### B01：电池标志位映射错误

当前使用 `BatteryFlag & 4` 判断 low，`& 8` 判断 critical，`SystemStatus & 8` 判断节电。微软定义分别是：low=2、critical=4、charging=8，节电开启状态=1。`BatteryFlag=255` 表示未知，也应与“无电池”区分。来源：[SYSTEM_POWER_STATUS](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-system_power_status)。

**本次复现**：输入 low=2，程序输出 `low=false`；输入 critical=4，输出 `critical=false`；输入 charging=8，输出 `critical=true`；输入节电=1，输出 `onBatterySaver=false`。因此真实危急电量不能触发预期的退出分支；充电被误认作危急，但 worker 的 AC 守卫会在正常插电时挡住退出，不能声称“所有充电都会退出”。

修复：更正原生层常量，显式保留未知 AC/电池状态，不让未知值替用户选择电池动作。回归必须从原始 `SYSTEM_POWER_STATUS` 位开始覆盖 2/4/8/128/255、AC 0/1/255 与节电 0/1，不能只喂给上层一个已经构造好的 `critical=true`。

### B02：多屏坐标与发送结果

`NudgeMouse` 用整个虚拟桌面尺寸归一化坐标，却只发送 `MOUSEEVENTF_MOVE | MOUSEEVENTF_ABSOLUTE`。未带 `MOUSEEVENTF_VIRTUALDESK` 时，Windows 将绝对坐标映射到主屏，多屏布局存在坐标错位。来源：[MOUSEINPUT](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-mouseinput)。本次没有在物理多屏上移动鼠标，坐标错误的结论来自实现与官方契约的直接冲突。

另一个问题已经隔离复现：让 `SendInput` 返回 0，读取到的鼠标位置保持不变，方法仍返回 `true`。因为它只检查最终位置，没有检查成功插入的事件数，worker 因而可能累计虚假的成功心跳。

修复：采用虚拟桌面标志，验证发送数量和最终位置；分别报告发送被拒、部分发送、未归位。验收覆盖副屏位于左侧的负坐标、多 DPI、边缘像素，并用真实空闲计时确认有效性。

### B03：参数应用与响应不一致

`Start-KaProtection` 判断是否重启时遗漏 `reassertSec`、`batteryAllowDisplayOff`；后者也没有写入 worker 状态供比较。本次让其他参数一致，仅把重声明周期从 60 改为 90、低电量允许熄屏从 true 改为 false，结果 `stopCalls=0`、`restarted=false`，却返回 `applied.batteryAllowDisplayOff=false`。

此外 `applied` 缺少 `reassertSec`，网页 `doStart` 的比较会把 `undefined` 转为 NaN，从而使正常启动也可能出现“参数被调整”的提示。

修复：建立唯一的运行参数清单，用它生成 worker 参数、状态字段、比较与响应；区分 requested / effective。验收逐项只变更一个运行参数，验证 worker 实际取值；完全相同的无限期请求应复用现有 worker。

### B05：起停与看门狗没有共同事务边界

启动顺序是“发现或创建 worker → 等待就绪 → 写 awake 意图”。看门狗只锁住自己的同类进程，不与 CLI / 网页 / 托盘的起停共享操作锁。

**本次受控复现**：初始 intent=off；worker 已创建、启动函数尚未写 intent 时插入一次对账；看门狗读到 off 并停止 worker；启动函数继续写 awake，最终 `Ok=true`、intent=awake、worker 已停止。现有 worker 单实例锁只能限制数量，不能保证整次操作一致。

修复：按规范化数据根 + 用户标识建立共用操作锁，覆盖 start / stop / reconcile 的读、决策、写入、验证，配合 operationId 或 revision；避免嵌套锁和持锁调用自身造成死锁。验收要控制时间点覆盖 start/stop、start/reconcile、双 start、重参数化/reconcile，确认最后一次已提交操作与现场一致，失败不得报成功。

### B06：备份失败后继续 apply

`[void](Write-KaJson $backupPath ...)` 丢弃失败结果，随后仍执行 AC/DC 写入。本次将备份写入替换为 false，仍观察到两次 `/set*valueindex`，最终 `Ok=true`，备份不存在。

修复：任何 AC/DC 值变更之前，必须确认原值可读、备份成功持久化且读回校验通过，否则明确失败；多步修改有部分失败时按已验证备份回滚，并分别报告写入与验证结果。`/attributes` 的可见性修改也应纳入恢复边界的说明。验收覆盖目录只读、写失败、读回失败、原值未知和第二条设置失败。

### B07：跨电源计划重复 apply 丢失原值

复现前提：已有计划 A 的备份，用户切换到 B 再执行 apply。代码因备份存在而跳过备份，直接修改 `SCHEME_CURRENT`。restore 又会拒绝把 A 的备份写入 B，因此 B 的原值没有正常恢复路径。

近期修复建议：apply 发现现有备份不属于当前计划时直接拒绝，提示先处理已有备份；后续确有多计划需求再改为按 schemeGuid 分开保存。验收必须走 A apply → 切 B → B apply → 分别恢复，验证每个计划原值都不丢失。

### B08：无效备份被视作成功恢复

`Read-KaJson` 对损坏内容返回 null。restore 没校验备份结构，null 的 ac/dc 使后续比较走过“没有需要验证的值”分支。**本次复现**：备份内容为 `{broken`，没有 AC/DC 值写入，却返回 `Verified=true`、`lid.restore.ok`，并删除该文件。

修复：验证备份对象、schema、schemeGuid、found、AC/DC 值及范围；不可解析或不可验证时保留原文件。必须读回实际设置且字段完整吻合才允许删除备份。验收覆盖损坏 JSON、空对象、缺字段、范围外值与设置读回失败。

### B09：start API 输入验证不严格

**本次复现**：传入 `minutes="oops"`、`antiLock="false"`，handler 返回 200，实际传给核心的是 `minutes=0`、`antiLock=true`。错误时长变成无限期保护；PowerShell 对非空字符串的 bool 转换使 false 的含义翻转。

修复：在核心入口共享严格 schema，HTTP 层将错误映射为 400。API 的布尔字段只收 JSON boolean；数字只收有限数值、检查上下界；未知字段与非法枚举明确拒绝。人工编辑配置可继续使用现有兼容转换器，不能把它当作公开 API 契约。验收包括字符串、null、数组、负数、超大值、NaN/Infinity 的可达输入及正常数值，确认拒绝路径没有启动副作用。

### B10：共享 `.tmp` 不是多写者安全

每次写入使用同一个 `$Path.tmp`。两个调用者可以交错写入、移动或删除彼此的文件；任一失败分支还会尝试删除这个共享临时文件。配置读改写也缺少防止丢失更新的事务。

**本次实际复现**：4 个独立 runspace 对隔离目标共写 600 次，最终复跑 382 次返回失败；此前两轮为 360、402 次。数字随调度变化，不是生产故障率，但已经证明无 ACL/磁盘故障时竞争本身就能令写入失败。

修复：使用同目录唯一临时文件、只清理自己的临时文件、同一数据根的共用操作锁，并选择经过验证的同卷替换策略；读改写带 revision 检查。验收要求多进程同时写时没有残缺 JSON、没有误删其他写者文件、提交结果与 revision 一致，错误场景旧文件仍完整。单纯给临时名加 GUID 不能解决配置丢失更新或 B05。

### B11：保护证据认领了“活着的 PID”

`Get-KaProtectedSpan` 用 `state.json.pid` 加 `Get-Process` 判断历史 worker 仍存活，没有校验脚本、数据根和进程创建时间。Windows 的 PID 可以复用，状态文件又会跨退出/重启保留。

**本次复现**：把夹具 state 指向审查脚本自身的真实 PID，startedEpoch 设为两小时前、没有任何保护日志，结果仍生成 7200 秒的“保护时间段”，`known=true`。

修复：复用经过归属校验的 worker 发现结果，并校验创建时间或 worker instanceId；不能确认时显示 unknown。验收用同 PID 不同命令行、错误数据根、错误创建时间、重启残留状态与正常运行状态覆盖，不允许无关进程建立保护时间段。

### B12：单个请求阻塞整个面板

server 串行执行 `GetContext → Read-KaBody → handler`；读请求体采用同步阻塞，应用没有自己的短截止时间。HTTP.sys 可能最终按其超时终止连接，但在此之前所有请求共用的循环已被占住。

**本次真实复现**：发送合法本地请求头，声明 1024 字节的 config 请求体但只送出 `{}`；随后 ping 在 1.5 秒客户端期限内超时。关闭前一个连接后 ping 恢复 200。没有实际完成配置修改。该实验模拟有权调用本地 API 的慢调用者，不证明外部网页能够绕过既有请求头限制。worker 是独立进程，面板阻塞不等于电源请求立即失效。

前端同时存在无 timeout、`setInterval` 不等待上次请求的问题：隔离触发 3 次 tick 后留下 3 个未完成请求，`AbortController` 未使用，长操作会积累轮询。

修复：请求体设截止时间，慢查询/操作设界限，采用有上限的并发处理；写操作仍通过 B05 的共用锁串行提交。前端对同类轮询至多保留一个请求，增加超时与退避，隐藏页面降低刷新。操作超时后重新查询 operationId 状态，不能直接重试 start/stop。验收覆盖半截请求体、长报告、多标签页及服务关闭后的按钮恢复。

## 测试与维护的改进方向

当前测试体系的优势是有真实进程、HTTP、安装器和突变测试；薄弱处在于不少断言验证的是“上层拿到的值”而不是底层契约，或者单入口顺序操作，没有跨入口交错。因此基础门禁通过与上述缺陷并不矛盾。

建议形成四层验收：

1. **纯逻辑与原生边界**：原始位字段、schema、运行选项清单、备份状态机、证据归属；以独立官方契约和故障注入作预期，避免复制实现。
2. **跨进程一致性**：真实多进程读改写、受控起停竞争、进程退出/重启、不可写文件、实例身份变化；所有数据根隔离。
3. **浏览器与界面**：启动/停止/改参数/中文英文/失败重试/键盘操作；使用真实 Chromium 或 Edge 验证 DOM、焦点、按钮状态和超时，补截图。本次仅做 JS 语法与函数隔离实验。
4. **系统与分发**：在可丢弃 Windows VM 上跑完整行为、安装卸载；Win10/Win11、S3/S0、标准用户/管理员、单屏/多屏/RDP/锁屏列出结果。云端 Windows runner 不能代替笔记本合盖、充放电和物理待机验收。

新增的每个修复都要有能令原版本失败的场景。优先把本次 11 个缺陷转换为可持续回归，不必继续扩大“测试测试脚本”的数量来替代真实业务边界覆盖。

维护上，`ka-core.ps1` 已有约 3956 行，并混合原生调用、文案、持久化、生命周期和证据逻辑。先固定参数/结果/状态 schema 与上述回归，再按原生、存储、保护生命周期、证据、文案拆分。保留一个公共核心入口，避免三个界面各自解释参数；不建议在修复前同时改框架和重写所有界面。

## MCP：值得做，先完成任务级保护

推荐场景是“AI 开始长时间构建、推理或批处理时申请保护，结束时释放自己的保护；用户能查看是谁申请的、何时到期”。现有本地 HTTP API 可以复用业务能力，但它还不是 MCP：缺少协议消息、工具 schema、协议版本兼容、客户端生命周期和任务所有权。

优先建立 **lease（带所有者和期限的保护申请）**，再增加 MCP 适配。当前只有一个全局 intent，若直接把 start/stop 暴露为工具，两个 AI 客户端和手动操作会互相覆盖，任务 A 结束可能停止仍在运行的任务 B。

### 推荐接口与行为

| 工具 | 输入 | 输出与约束 |
| --- | --- | --- |
| `keepawake_status` | 无 | 保护状态、实际引擎状态、申请摘要、告警；默认不返回用户名和完整路径 |
| `keepawake_acquire` | reason、minutes、keepDisplayOn、antiLock、requestId | 返回 leaseId、leaseToken、expiresAt 与 effective；reason 限长，minutes 默认 30，上限 1440，不接受模型无限期申请 |
| `keepawake_renew` | leaseId、leaseToken、minutes、requestId | 只更新所属申请；不影响其他任务，也不修改全局默认 |
| `keepawake_release` | leaseId、leaseToken、requestId | 幂等释放自己的申请；其他申请仍有效时继续保护 |
| `keepawake_evidence` | hours | 返回有界、脱敏的统计与 unknown 状态；默认最多 24 小时，完整日志另行显式导出 |

建议首版不提供系统设置写入、任意 shell、任意 PID 停止、全局 unguard 或修改合盖动作的工具。用户仍可从本地界面执行现有显式管理操作。工具描述直接说明行为、期限和实际结果，避免让模型把“电源请求已登记”解释成“物理机器绝对不会睡”。

申请由服务端生成随机 ID 与能力 token；owner 由适配器/本地进程上下文绑定，不信任调用参数自报 owner。token 不进入日志或普通状态输出；本地同账户进程依然属于现有信任范围，这不是针对本机恶意软件的隔离。

聚合规则建议固定：有任一有效申请即保持系统；显示常亮和防锁屏取所有有效申请的 OR；输入方式采用用户配置，避免客户端相互切换；全局电池安全规则优先。纯任务申请到期只释放自身。手动“全部停止”应撤销所有申请并阻止旧续租自动恢复，用户再次明确启动后才解除暂停。界面用一张任务列表呈现原因、来源和到期时间。

正常关闭 MCP 适配器时释放其会话申请；异常退出靠过期时间兜底。必须允许客户端为长任务续租，并在续租失败时明确提示，不能让客户端以为仍受保护。是否跨系统重启保留任务由申请属性明确，首版 AI 会话申请默认不跨系统重启，手动常驻保护维持现有用户选择。

### 推荐实现与兼容性

采用**可选的 C# MCP 配套程序 + 官方 SDK + stdio**；主产品继续保持 Windows 内置 PowerShell 即可运行。MCP 配套程序可以独立发布为带运行时的包，体积、冷启动与 ARM64 包需要实际构建后衡量；不把可选依赖说成现有产品仍然“全部零第三方依赖”。官方 C# SDK 已支持 stdio，参考 [官方仓库](https://github.com/modelcontextprotocol/csharp-sdk) 与 [传输文档](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/transports/transports.html)。

建议新增位置：`integrations/mcp/` 存 SDK 适配器、固定依赖与测试；`ka-automation.ps1` 提供受 schema 限定的机器接口；核心增加 `ka-leases.ps1` 管理申请，仍由现有 worker 持有实际电源请求。初版可以通过受控 PowerShell 子进程调用核心，给冷启动设超时；只有测量确认调用延迟不可接受后再增加常驻内部通道。不要让适配器自行实现第二套保护引擎。

stdio 由客户端启动本地子进程，协议消息走 stdin/stdout，日志走 stderr；stdout 不能混入 Write-Host、进度或其他非协议文本。依据：[MCP stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)。它适合此项目的本地用途，也不需要把 8791 端口改成对外服务。

本次官网 latest 指向 `2026-07-28`。实现时固定具体 SDK 版本和支持的协议版本，用实际目标客户端做互操作验收；不要默认所有客户端都支持最新版本。HTTP MCP 可以以后再加，届时按 [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) 单独落实 Origin 校验、本地绑定与认证，现有固定 X-Ka-Client 不是身份凭证。

MCP 验收至少包括：两个客户端并行申请/独立释放；重复 requestId 不重复申请；过期、异常退出和续租失败；取消请求后的事务结果；协议日志不污染 stdout；中英文输出；模型拿不到其他申请 token；本地工具与 MCP 同时操作时最终状态一致。只读工具标明只读；写工具按宿主支持配置确认策略，不能只靠描述文本作权限控制。工具 schema 与输出见 [官方工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)。

**隐私说明需要更新**：MCP 服务自身可以完全不主动出网，但返回给 AI 客户端的数据可能由客户端发送给其模型服务。默认只返回最小状态；路径、用户名、日志、应用名和完整诊断报告需要脱敏或显式导出。不能在连接 MCP 后继续笼统承诺“数据绝不离开本机”。

## 其他值得扩展的功能

以下均为建议能力，当前代码尚未交付这些功能；“小/中/大”表示相对工作量，包含必要验证，不是排期承诺。

| 优先顺序 | 功能 | 用户获得什么 | 实现位置与依赖 | 关键验收 | 工作量 |
| --- | --- | --- | --- | --- | --- |
| 1 | 跟随任务的命令包装：`ka run -- <命令>` | 编译/下载/推理期间自动保护，任务结束自动释放 | CLI + lease；保存 PID 和创建时间，约束子进程树范围 | 正常、失败、Ctrl+C、进程不存在均释放自己的申请，保留原命令退出码 | 中 |
| 2 | 多任务保护列表 | 知道谁还需要电脑醒着，单独停止任务 | 核心 lease + 网页 + 托盘 | A 结束不影响 B；过期、重启、重复请求无幽灵任务 | 中 |
| 3 | MCP 本地接入 | AI 长任务可自主申请/释放且可查证 | 前述可选适配器；依赖 1/2 的所有权基础 | 两个目标客户端端到端实测后才声明兼容 | 中 |
| 4 | 精确结束时间与临时暂停 | 网页/托盘直接选“到明早九点”、暂停 15 分钟 | 复用 CLI 现有时间解析，增加 pausedUntil | 跨日、时区/DST、时间调整、暂停结束与手动停止优先关系明确 | 小到中 |
| 5 | 一键脱敏诊断包 | 报 bug 不必手工删用户名和路径 | report/evidence/log 的显式导出，先预览 | 默认无用户名、机器路径、token、无关进程信息；离线生成 | 小到中 |
| 6 | 保护异常通知 | worker 退出、请求失败、电量动作、证据发现异常时及时知道 | 统一事件 + 托盘通知；同类消息去重 | 通知只在状态变化时出现；锁屏、勿扰、无人登录时不假称已送达 | 中 |
| 7 | 场景预设 | 一键选“后台任务”“演示”“远程工作” | 预设仅映射现有参数，不新增引擎 | 预览有效参数，明确“允许锁屏但保持系统”的选项；不能绕过组织策略 | 小 |
| 8 | 电池/供电独立策略 | 拔电后自动采用更保守的保护与到期规则 | 修复 B01 后的状态机 + lease 聚合 | 未知电量不误判、迟滞、防抖、插拔电、真实低电量与显示空闲联测 | 中 |
| 9 | 托盘常驻与全局快捷键 | 不开浏览器即可开始、暂停、查看原因 | 单独的托盘登录项，不能与 guard 自动恢复混为一件事 | 快捷键冲突、重复托盘实例、退出托盘与停止保护语义清楚 | 小到中 |
| 10 | 指定程序运行时保护 | 长期按需绑定某个编译器或工作程序 | 明确授权的进程规则；创建时间/实例身份 | 不收集窗口标题，PID 复用不误认；不凭“进程还活着”假定任务仍在工作 | 中 |
| 11 | 用户制定的时间表 | 工作日指定时段保护、夜间释放 | 本地调度规则 + lease；手动停止有优先级 | 错过触发、休眠唤醒、DST、规则冲突、停用恢复均可解释 | 中 |
| 12 | 最小界面与可访问性 | 常用操作一眼可见，复杂诊断按需展开 | 保留主状态、开始/停止、时长；高级项折叠；语义标签与焦点完善 | 键盘完整操作、放大 200%、窄窗口、对比度、屏幕阅读器 | 中 |

其中“跟随进程”有成熟同类先例：微软 PowerToys Awake 已公开支持 `--pid` 和 `--use-parent-pid`，但本项目还应额外处理多任务并存和 PID 身份，见 [官方说明](https://learn.microsoft.com/en-us/windows/powertoys/awake)。

不建议现在加入云账号、跨设备同步、外网控制面板或大规模 UI 框架迁移：它们增加运维与安全面，对本地长任务保护的直接收益较低。CPU/网络流量“智能猜任务”也应排在明确任务包装与用户规则之后，避免误判为无人工作而释放保护。

## 建议落地顺序

| 阶段 | 内容 | 完成条件 |
| --- | --- | --- |
| 第一阶段：可靠性补丁 | B01、B05、B06、B07、B10；随后 B02/B03/B08/B09/B11/B12 | 每个修复有能击中旧实现的回归；隔离与真实进程测试通过；完整套件在一次性 VM 上通过 |
| 第二阶段：统一自动化基础 | 严格输入/结果 schema、共用操作锁、instanceId、lease、机器接口、任务包装 | 手动与两个自动任务并发起停无互相覆盖；历史配置和意图迁移可回退 |
| 第三阶段：MCP 最小可用版 | stdio 适配器、status/acquire/renew/release/evidence、脱敏、目标客户端样例 | 实际连接目标客户端完成长任务、异常断开和并行任务验证；更新隐私说明与可选包清单 |
